## Slide 2: 问题与动机

### 传统舆情监控的痛点

| 痛点 | 具体表现 |
|------|---------|
| **信息过载** | 每天数百条财经新闻，人工无法逐一阅读 |
| **情绪滞后** | 传统研报发布周期 T+1，错过最佳决策窗口 |
| **维度单一** | 只有"正面/负面"标签，缺少恐惧/贪婪/不确定等细粒度情绪 |
| **关联缺失** | 看不到新闻背后的实体关系和因果传导链 |
| **被动获取** | 无法按个人关注的关键词主动推送告警 |

### 我们的回答

> 构建一个**实时采集 → 智能评分 → 深度分析 → 主动推送**的闭环系统，
> 让交易员在 1 分钟内感知市场情绪变化，在情绪拐点时收到告警。

📌 先讲痛点，再引出方案。听众（交易员/量化开发者）对"信息过载"和"情绪滞后"有切身体会。

⏱ 2 分钟

## Slide 5: 技术选型与权衡

| 层级 | 选型 | 理由 | 考虑过的替代方案 |
|------|------|------|-----------------|
| 后端框架 | **FastAPI** | 原生 async、自动 OpenAPI、高性能 | Flask（同步）、Django（过重） |
| 情绪模型 | **FinBERT (DistilBERT)** | 金融预训练、多语言、CPU 可推理 | VADER（太粗糙）、GPT API（太慢太贵） |
| 深度分析 | **DeepSeek Chat** | 中文强、成本低、长上下文 | GPT-4（贵）、Qwen（中文弱于 DeepSeek） |
| 数据库 | **SQLite + aiosqlite** | 零配置、单文件、够用 | PostgreSQL（需运维，当前规模不需要） |
| 实时通信 | **WebSocket** | 双向推送、低延迟 | SSE（单向）、轮询（延迟高） |
| 前端 | **Vue 3 + Composition API** | 轻量、响应式、学习曲线低 | React（偏重）、Svelte（生态小） |
| 图表 | **Chart.js + Canvas** | 灵活、轻量 | ECharts（过重）、D3（太底层） |
| 部署 | **Docker Compose** | 一键启动、环境隔离 | K8s（当前规模过重） |

📌 重点讲"为什么不用替代方案"——技术选型的价值在于取舍，不是选最流行的，而是选最适合当前阶段的。

⏱ 2 分钟

## Slide 6: 数据管线详解

```
                    Fast Track (< 1s)                    Slow Track (10-30s)
                    ┌────────────┐                      ┌──────────────────────┐
  Crawler ──▶ Dedup│ FinBERT    │──▶ scored_queue ──▶  │ DeepSeek LLM         │
  (30s轮询)  (MD5) │ 评分+标签   │     │               │ ├ 实体提取            │
                    └────────────┘     │ |score|>0.5   │ ├ 多维情绪(fear/greed)│
                                       ↓               │ ├ 事件聚类            │
                                  ┌──────────┐         │ ├ 知识图谱+因果链     │
                                  │ 告警判断  │         │ └ 深度研报            │
                                  │ info/    │         └──────────┬───────────┘
                                  │ warning/ │                    ↓
                                  │ critical │             ┌──────────┐
                                  └────┬─────┘             │ DB 持久化 │
                                       ↓                   └────┬─────┘
                                  WebSocket Push                ↓
                                  (实时推送前端)          11 张表存储
```

### 关键设计决策

1. **双轨解耦**：Fast Track 和 Slow Track 通过队列异步解耦，不互相阻塞
2. **阈值触发**：只有 |score| > 0.5 才进 Slow Track，避免对中性新闻浪费 LLM 调用
3. **5 项并行**：Slow Track 内 5 项分析并发执行，总耗时 = max(各项) 而非 sum
4. **ProcessPool**：FinBERT 在独立进程池中运行，不阻塞事件循环

📌 用"双轨"类比高速公路：快车道（FinBERT）所有车都走，慢车道（DeepSeek）只有大车（高情绪新闻）才进。

⏱ 2.5 分钟

## Slide 7: 核心功能展示 — 情绪趋势与多维分析

### 7.1 情绪趋势图

```
  +1.0 ┤     ╭──╮        ╭──── MA 线（5点移动平均）
       │    ╱    ╲       ╱
   0.0 ┤───╱──────╲────╱───── 零线
       │  ╱        ╲  ╱
  -1.0 ┤╱            ╲╱
       └──┬──┬──┬──┬──┬──▶ 时间
          │  │  │  │  │
          ▽  ▽  ▽  ▽  ▽     情绪分布条 (pos/neu/neg)
                △             动量拐点标记
```

- **小时级聚合**：从分钟级（100+ 噪声点）升级到小时级（24 个清晰点）
- **MA 平滑**：5 点移动平均消除短期波动，揭示趋势方向
- **波动带**：min/max 半透明区间显示分歧度
- **区域填充**：MA 线下方填充色（正=绿，负=红），一眼看出情绪偏向
- **分布条**：每个时间点下方显示 positive/neutral/negative 比例
- **拐点标记**：momentum_shift 事件用三角形标注，按小时分组避免重叠

### 7.2 多维情绪雷达

- 四维：fear / greed / optimism / uncertainty
- 动量拐点检测：当前情绪 vs 历史均值，偏移超过阈值时标记 momentum_shift
- 按实体独立分析：同一新闻对不同实体（如央行 vs 银行）情绪可能截然不同

📌 如果现场有数据，可以切换到浏览器实时展示。趋势图是整个仪表盘最核心的可视化。

⏱ 2 分钟

## Slide 8: 核心功能展示 — 实体、事件与知识图谱

### 8.1 热门实体云

- 按出现频率排序，按情绪着色（绿=正面，红=负面，灰=中性）
- 点击实体 → 查看该实体的情绪时间线
- 实体有别名系统：央行 = 人民银行 = PBOC

### 8.2 事件聚合时间线

- **聚类算法**：新新闻的实体集合与已有事件做 Jaccard 相似度匹配
- **匹配 → 合并**：实体重叠度 > 阈值，归入已有事件，更新情绪均值
- **不匹配 → 新建**：创建新事件簇，LLM 生成事件标题
- **显著性评分**：`significance = min(count/10, 1) × 0.5 + min(|avg|, 1) × 0.5`

### 8.3 知识图谱

- **关系抽取**：LLM 从新闻中提取实体间关系（如"央行 → 降息 → 银行"）
- **因果链推理**：给定一组实体，推理最关键的因果传导路径
- **置信度**：每条关系带 confidence 分数，低置信度关系可过滤

📌 三者形成递进关系：实体是原子，事件是实体的组合，知识图谱是事件间的关系网络。

⏱ 2 分钟

- 支持**追问**（基于已有报告上下文）和**多模型对比**（魔鬼代言人视角）

```json

{"type": "sentiment", "payload": {"score": -0.7, "label": "negative"}}
```

📌 强调 WebSocket 是"推"不是"拉"——服务端主动推送，前端无需轮询。这是实时性的关键。

## Slide 11: 数据库设计

### 11 张表，3 层关系

```
news ──1:N── sentiment ──1:1── alerts
  │                      │
  └──M:N── entities ─────┘
              │
              └──1:N── multi_sentiment
              │
              └──M:N── entity_relations

event_clusters (独立，引用 entities + news_ids)
reports (独立，冗余存储新闻/情绪字段便于独立查询)
subscriptions (独立，按 user_id 组织)
fed_policy_summary (独立，1h 缓存快照)
```

### 设计决策

- **reports 冗余字段**：`news_title`/`news_source`/`sentiment_score` 等冗余存储，避免 JOIN 查询，提升列表页性能
- **entities 别名**：`aliases` 字段存 JSON 数组，支持 "央行" = "人民银行" = "PBOC" 的多对一映射
- **event_clusters JSON**：`entities_json`/`news_ids_json` 用 JSON 存储，SQLite 原生不支持数组类型
- **SQLite 选择**：零配置、单文件部署、当前单机场景够用；后续可迁移到 PostgreSQL

📌 如果听众问"为什么不用 PostgreSQL"，回答：当前阶段单机部署，SQLite 零运维成本。表结构已兼容迁移。

⏱ 1.5 分钟

## Slide 14: 敏捷实践详解

### 1. 用户故事驱动

```
作为交易员，
我想在美联储政策转向时第一时间收到告警，
以便在降息/加息前调整债券仓位。

→ 拆解为：
  • 爬虫采集 Fed 相关新闻
  • FinBERT 评分判断情绪
  • Slow Track 深度分析政策含义
  • 订阅 "美联储" 关键词 + 阈值 -0.5
  • WebSocket 推送告警到前端
  → 后续扩展为 Fed Policy 独立栏目
```

### 2. 垂直切片

每个功能从**数据层 → 逻辑层 → API 层 → 前端层**完整实现：

```
Fed Policy 栏目的垂直切片：
  app/db.py          → 新增 fed_policy_summary 表
  app/repository.py  → save/load 函数
  app/analysis/      → fed_policy.py 模块
  app/api/routes.py  → /fed-policy 端点
  frontend/          → FedPolicy.vue 组件

```

## Slide 15: AI 辅助开发实践

### 人机协作模式

本项目全程使用 **Claude Code (CLI)** 作为 AI 结对编程伙伴：

```
┌──────────┐     ┌─────────────────────────────────────┐     ┌──────────┐
│  人类     │────▶│  Claude Code                        │────▶│  代码     │
│          │     │                                     │     │          │
│ 定义需求  │     │ 1. 探索代码库，理解上下文            │     │ 新模块    │
│ 审核方案  │     │ 2. 制定实现计划 (Plan Mode)         │     │ 新测试    │
│ 确认方向  │     │ 3. 实现代码 + 测试                  │     │ 新文档    │
│ 修正偏差  │     │ 4. 运行测试验证                     │     │ Bug 修复  │
└──────────┘     └─────────────────────────────────────┘     └──────────┘
```

### 典型协作场景

| 场景 | 人类角色 | AI 角色 | 耗时 |
|------|---------|---------|------|
| 新增 Fed Policy | 定义需求、审核 Plan | 创建 6 个文件（模块/路由/组件/测试/DB/文档） | ~15 min |
| 修复"暂无数据" | 发现问题、确认方向 | 跨 4 个组件定位 API 路径不匹配 | ~5 min |
| 优化趋势图 | 确认小时级聚合方案 | 重写后端聚合逻辑 + 前端图表渲染 | ~10 min |
| 重构测试体系 | 确认分层策略 | 统一 conftest、重写 10 个测试文件、写文档 | ~20 min |

### 效率对比

| 指标 | 纯人工估算 | AI 辅助实际 | 提升倍数 |
|------|-----------|------------|---------|
| 新模块开发 | 2-4 小时 | 15-30 分钟 | 4-8x |
| Bug 定位 | 30-60 分钟 | 3-5 分钟 | 6-12x |
| 测试编写 | 1-2 小时/模块 | 5-10 分钟/模块 | 6-12x |
| 文档撰写 | 2-3 小时 | 10-15 分钟 | 8-12x |

📌 关键不是"AI 写代码"，而是"人定义方向，AI 执行细节"。人类做决策，AI 做实现——这才是高效协作。
